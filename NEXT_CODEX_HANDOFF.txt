2. What the system does
======================================================================

High-level workflow:
  1. app.py starts the whole system.
  2. tshark/Wireshark captures HTTP traffic on selected interface and port.
  3. Captured traffic becomes batch files under input/ such as input/1.1.n.txt.
  4. RAW HTTP logs are written into MySQL.
  5. Detection V2 runs layered detection:
     - Payload model
     - POC rule engine
     - Behavior window model
     - Fusion scoring
  6. Normal traffic remains raw_only.
  7. Suspicious candidate traffic enters the LLM review queue.
  8. LLM/RAG final review decides whether it becomes a formal attack event.
  9. Confirmed attacks are written into MySQL and displayed on the dashboard.
  10. Situation awareness correlates multiple actions from the same attacker/source group.
  11. AI situation reports and professional reports are generated through Bailian API.
  12. Auto defense can block source IPs with Windows firewall rules.

Core distinction:
  raw_only:
    Raw traffic stored for evidence and future analysis. It should not be treated as a formal attack.

  candidate:
    Suspicious traffic after small-model/rule/behavior fusion. It is waiting for LLM review or manual review.

  attack_event:
    A confirmed attack event after final review. Only this should be shown as real attack evidence in the main dashboard.

  situation:
    A correlated attacker behavior chain. It is not one packet. It is a sequence such as scan -> brute force -> SQL injection -> XSS from one source or a proxy group within a time window.

9. Known bugs, incidents, and lessons
======================================================================

Recurring serious problem:
  Several times the server appeared healthy but detection did not produce expected events.
  Causes have included:
    wrong capture interface
    wrong monitored port
    lab not actually running
    old/new chain conflict
    LLM queue backlog
    Ollama pressure
    polling delays
    disk full from logs/capture/result/report artifacts
    frontend reading stale data

Most important troubleshooting sequence:
  1. Confirm target service/lab is listening on the expected port.
  2. Confirm app.py capture config says the same port.
  3. Confirm selected interface:
     - External traffic normally Ethernet, often interface 4 on the server.
     - Local 127.0.0.1 test normally loopback, often interface 5.
  4. Confirm input/ is receiving new files.
  5. Confirm RAW logs are inserted into MySQL.
  6. Confirm candidate/event rows are being created.
  7. Confirm LLM review queue is not stuck.
  8. Confirm API is running on 3049.
  9. Confirm frontend on 1145 is loading fresh data.
  10. Confirm disk space is not exhausted.

Specific known historical bugs:
  - app.py once had mojibake/unterminated string syntax error due to encoding damage.
  - db_config.json with UTF-8 BOM caused JSONDecodeError; fix was utf-8-sig reading.
  - Dashboard once exited immediately because port/process conflicts or stale process.
  - Normal login traffic was once misclassified as high risk; training and threshold tuning reduced this.
  - Attack types repeated or were displayed as duplicated categories; frontend aggregation needed cleanup.
  - Attack source geography was once fake/overcrowded; later reduced to TOP7 and simplified location labels.
  - Some frontend Chinese text became mojibake; preserve UTF-8.
  - Fast defense initially did not block/unblock reliably.
  - Blocking only one direction was insufficient; inbound and outbound Windows firewall rules are needed.
  - Auto defense was too slow when waiting for full LLM chain; fast deterministic rules were added.
  - If auto defense blocks an IP, unblocking must remove all matching inbound/outbound rules.
  - Situation awareness did not always show port scan/lab events due to rule thresholds and event pipeline mismatch.
  - RAW/AG/b events confused user and judges; UI should clearly reflect final reviewed events.
  - RAG references were shown even when RAG disabled; frontend/backend guard was needed.
  - CPU display once showed 0%; check system metric collection.
  - Professional report had large blank pages, orphan headings, duplicate tables, and garbled numbering.
  - Background image from an old user-provided photo was supposed to be removed. bg-main.jpg was deleted in latest commit.

10. Acceleration measures already used
======================================================================

1. Small-model/rule/behavior pre-filtering:
  Only high-value candidate traffic goes to LLM.

2. Ollama warm start / keep-alive:
  Keeps local model loaded to avoid cold start.

3. Fixed model selection during demonstration:
  Avoids repeated model loading.

4. 4000 lab fingerprint fast path:
  Exact known demo payloads can output faster.

5. Reduced polling interval:
  Some sync loops reduced from 5 seconds to 1 second.

6. Async process separation:
  capture, detection, db, LLM, API, frontend, situation, lab are separate processes.

7. Watchdog/supervisor:
  Restarts unhealthy child processes or full process tree.

8. Bailian API for long reports:
  Professional and situation reports should not block local Ollama.

9. RAG switch:
  Allows disabling RAG to reduce cost/time.

10. Evidence summary before LLM:
  Intended direction is to send compact structured evidence instead of huge raw logs.

Future acceleration ideas already discussed:
  - Replace directory polling with file/event notification.
  - Use a lightweight in-memory or durable message queue.
  - Cache common attack template results.
  - Tiered LLM calls: small cloud model for simple cases, stronger model for complex cases.
  - Prebuild structured evidence summaries before LLM.

Highest-value four:
  - Small model pre-filtering before LLM
  - 4000 lab fingerprint fast path
  - Event-driven pipeline instead of polling
  - Prebuilt evidence summaries to reduce LLM input size

11. How to answer common judge questions
======================================================================

Q: What is different from a firewall?
  A firewall mainly enforces allow/deny at network or rule level. This system preserves request/response evidence, performs application-layer semantic detection, correlates multi-step attacker behavior into situations, uses LLM/RAG for explainable review, and generates investigation/defense reports. It can also call firewall rules for blocking, but the core value is situation awareness and evidence-driven explanation.

Q: What are the small models trained on?
  The current project has legacy MLP artifacts and V2 payload/behavior models. The training scripts are in scripts/train_*.py. Training data includes synthetic Web attack/normal samples, hard negatives such as normal login traffic, and behavior windows for scanning/bruteforce/high-frequency traffic. Be careful: do not overclaim a huge public dataset unless verified in code.

Q: What is RAG implemented with?
  Legacy: SQLite FTS5 style DB at llm/rag/rag_knowledge.db.
  Advanced: MySQL metadata + LanceDB vectors + BM25 + RRF + qwen3-rerank.
  Embeddings: Bailian text-embedding-v4.
  Sources: project seed + OWASP + MITRE ATT&CK + CISA KEV.

Q: Where is the database?
  Main runtime DB is MySQL traffic_pipeline. On server it uses port 3307. Do not delete or reset it.

Q: Accuracy and speed?
  Historical internal tests showed very high numbers on small curated test sets. Be honest: say that competition demos use controlled/lab traffic plus real server traffic observations; exact final metrics should be read from current docs/tests/logs before presenting.

Q: Did you test 0-day?
  It does not truly detect unknown 0-days by name. It detects suspicious unknown patterns through behavior, payload anomaly, endpoint context, response behavior, and situation correlation. The lab includes unknown/0-day-like synthetic traffic structures for demonstrating anomaly handling, not real 0-day exploitation.
